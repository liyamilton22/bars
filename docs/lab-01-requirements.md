# Лабораторная работа №1 — Техническое задание

## 1. Название проекта

**Информационная система мониторинга сроков и этапов выполнения работ при реконструкции сетевых объектов**

**Организация-заказчик:** АО «Сетевая компания»

---

## 2. Предметная область

АО «Сетевая компания» выполняет работы по реконструкции сетевых объектов. В процессе выполнения работ необходимо контролировать этапы реконструкции, сроки их выполнения и ответственных исполнителей.

В настоящее время информация о ходе выполнения отдельных этапов может храниться в разных документах и системах. Из-за этого может быть сложно быстро определить текущее состояние работы, ответственного исполнителя и наличие отклонений от плановых сроков.

Разрабатываемая информационная система предназначена для регистрации заявок на контроль этапов реконструкции и отслеживания их состояния.

Диспетчер или специалист по управлению реконструкцией создаёт заявку, указывает её заголовок, сетевой объект и описание. После создания заявки диспетчер отдельно назначает исполнителя.

Исполнитель после входа в систему видит назначенные ему заявки и может перевести свою заявку в работу. После выполнения этапа исполнитель закрывает заявку.

Диспетчер может просматривать заявки и контролировать их текущее состояние. При необходимости заявка может быть отменена.

Таким образом, основным процессом системы является создание, назначение, выполнение и закрытие заявки на контроль этапа реконструкции.

---

## 3. Главная сущность

Главная сущность системы — **заявка на контроль этапа реконструкции**.

Каждая заявка имеет:

- `id` — машинный идентификатор;
- `number` — человекочитаемый номер заявки;
- `title` — заголовок;
- `siteId` — идентификатор сетевого объекта из справочника;
- `description` — описание;
- `executorId` — назначенный исполнитель;
- `status` — текущий статус;
- дату создания;
- плановый срок выполнения;
- фактический срок выполнения.

---

## 4. Справочник

В качестве справочника используются **сетевые объекты**.

Каждый сетевой объект имеет собственный числовой идентификатор `siteId`.

Заявка содержит только ссылку `siteId` на запись справочника, а информация о самом сетевом объекте хранится отдельно.

---

## 5. Роли и права

В системе предусмотрены две основные роли:

1. **Диспетчер / специалист по управлению реконструкцией**
2. **Исполнитель**

| Действие | Диспетчер | Исполнитель |
|---|---:|---:|
| Вход в систему | Да | Да |
| Просмотр списка заявок | Да | Да |
| Просмотр заявки | Да | Да |
| Создание заявки | Да | Нет |
| Указание сетевого объекта | Да | Нет |
| Назначение исполнителя | Да | Нет |
| Изменение статуса своей заявки | Нет | Да |
| Просмотр назначенных заявок | Да | Да |
| Закрытие своей заявки | Нет | Да |
| Отмена заявки | Да | Нет |
| Изменение чужой заявки | Нет | Нет |

Назначение исполнителя и изменение статуса являются разными действиями.

---

## 6. Граница системы

### Входит в учебную реализацию

В рамках семестра реализуются:

- авторизация пользователей;
- разграничение прав между диспетчером и исполнителем;
- просмотр списка заявок;
- создание заявки;
- просмотр информации о заявке;
- выбор сетевого объекта из справочника;
- назначение исполнителя;
- изменение статуса заявки исполнителем;
- отмена заявки;
- хранение данных в PostgreSQL;
- REST API на ASP.NET Core;
- клиентское приложение на Vue 3.

### Не входит в учебную реализацию

В рамках первой версии системы не реализуются:

- полноценная интеграция с внешними информационными системами предприятия;
- интеграция с BIM-системами;
- интеграция с ГИС;
- мобильное приложение;
- сложная аналитика;
- автоматический расчёт производственных показателей;
- расширенная система уведомлений;
- масштабирование системы на все процессы предприятия.

Эти возможности рассматриваются как направления дальнейшего развития проекта в рамках ВКР.

# 7. Функциональные требования

## FR-01. Авторизация

**Роль:** диспетчер, исполнитель.

Система должна предоставлять пользователю форму входа по логину и паролю.

После успешной авторизации пользователь должен получить доступ к функциям, соответствующим его роли.

---

## FR-02. Просмотр списка заявок

**Роль:** диспетчер, исполнитель.

Система должна отображать список заявок с информацией:

- номер;
- заголовок;
- сетевой объект;
- исполнитель;
- статус;
- дата создания.

Исполнитель должен видеть заявки, назначенные ему.

Диспетчер должен иметь возможность просматривать все заявки.

---

## FR-03. Создание заявки

**Роль:** диспетчер.

Диспетчер должен иметь возможность создать новую заявку.

При создании заявки должны быть заполнены:

- заголовок;
- ссылка на сетевой объект;
- описание.

После создания заявке автоматически присваиваются:

- машинный `id`;
- человекочитаемый `number`;
- статус `New`.

---

## FR-04. Выбор сетевого объекта

**Роль:** диспетчер.

При создании заявки диспетчер должен выбрать сетевой объект из справочника.

В заявке должен сохраняться числовой идентификатор выбранного объекта `siteId`.

---

## FR-05. Просмотр заявки

**Роль:** диспетчер, исполнитель.

Система должна предоставлять возможность открыть заявку и просмотреть её основные данные:

- номер;
- заголовок;
- сетевой объект;
- описание;
- исполнитель;
- статус;
- дату создания;
- сроки выполнения.

---

## FR-06. Назначение исполнителя

**Роль:** диспетчер.

Диспетчер должен иметь возможность отдельно назначить исполнителя для заявки.

После назначения в заявке должен быть сохранён идентификатор исполнителя.

Назначение исполнителя не должно автоматически изменять статус заявки.

---

## FR-07. Просмотр назначенных заявок

**Роль:** исполнитель.

После входа исполнитель должен видеть заявки, назначенные именно ему.

Исполнитель не должен иметь возможности изменять заявки, назначенные другим исполнителям.

---

## FR-08. Перевод заявки в работу

**Роль:** исполнитель.

Назначенный исполнитель должен иметь возможность изменить статус своей заявки:

`New → InProgress`.

Изменение статуса должно быть доступно только назначенному исполнителю.

---

## FR-09. Закрытие заявки

**Роль:** исполнитель.

После выполнения этапа реконструкции исполнитель должен иметь возможность изменить статус своей заявки:

`InProgress → Closed`.

После закрытия заявка считается выполненной.

---

## FR-10. Отмена заявки

**Роль:** диспетчер.

Диспетчер должен иметь возможность отменить заявку.

При отмене статус заявки изменяется на:

`Cancelled`.

---

## FR-11. Контроль статуса

**Роль:** диспетчер, исполнитель.

Система должна отображать текущий статус каждой заявки.

В API и базе данных должны использоваться четыре значения:

- `New`;
- `InProgress`;
- `Closed`;
- `Cancelled`.

---

## FR-12. Разграничение прав

**Роль:** система.

Система должна запрещать исполнителю:

- создавать заявки;
- назначать исполнителей;
- изменять чужие заявки.

Система должна разрешать исполнителю изменять статус только назначенных ему заявок.

---

# 8. Нефункциональные требования

## NFR-01. Сохранность данных

После перезапуска сервера созданные заявки, пользователи, назначения исполнителей и статусы должны сохраняться в базе данных PostgreSQL и быть доступны после повторного запуска системы.

---

## NFR-02. Время ответа

При работе с учебным объёмом данных основные операции API должны выполняться не более чем за 2 секунды при нормальной нагрузке.

---

## NFR-03. Безопасность доступа

Пользователь не должен получать доступ к операциям, запрещённым его ролью.

Проверка прав должна выполняться на стороне серверного API, а не только в интерфейсе.

---

## NFR-04. Совместимость

Клиентская часть системы должна быть реализована с использованием Vue 3.

Серверная часть должна быть реализована с использованием ASP.NET Core.

Для хранения данных должна использоваться PostgreSQL.

---

# 9. Статусы заявки

| Код | Назначение | Смысл на экране |
|---|---|---|
| `New` | Заявка создана | Новая |
| `InProgress` | Исполнитель приступил к работе | В работе |
| `Closed` | Работа завершена | Закрыта |
| `Cancelled` | Заявка отменена | Отменена |

Статус `New` устанавливается автоматически после создания заявки.

Статус `InProgress` устанавливает назначенный исполнитель.

Статус `Closed` устанавливает назначенный исполнитель после выполнения работы.

Статус `Cancelled` устанавливает диспетчер при отмене заявки.

# 10. Use Case — выполнение заявки

## UC-01. Выполнение этапа реконструкции

**Актёр:** Исполнитель.

**Предусловия:**

- исполнитель зарегистрирован в системе;
- исполнитель успешно вошёл в систему;
- заявка существует;
- заявка назначена этому исполнителю;
- заявка находится в статусе `New`.

### Основной поток

1. Исполнитель входит в систему.
2. Система проверяет логин и пароль.
3. Исполнитель открывает список назначенных ему заявок.
4. Исполнитель выбирает нужную заявку.
5. Система отображает данные заявки.
6. Исполнитель переводит заявку из `New` в `InProgress`.
7. Система сохраняет новый статус.
8. Исполнитель выполняет соответствующий этап работ.
9. После выполнения этапа исполнитель открывает заявку.
10. Исполнитель переводит заявку из `InProgress` в `Closed`.
11. Система сохраняет новый статус.
12. Заявка отображается как закрытая.

### Альтернативный поток

Если заявка не назначена текущему исполнителю, система не должна разрешать ему изменять её статус.

Если пользователь не имеет необходимых прав, система должна отказать в выполнении операции.

### Постусловие

Заявка находится в статусе `Closed`, если этап реконструкции выполнен.

# 11. Критерии приёмки

## AC-01. Создание заявки

**Дано:** диспетчер вошёл в систему.

**Когда:** диспетчер заполняет заголовок, выбирает сетевой объект, вводит описание и нажимает кнопку «Создать».

**Тогда:** система создаёт заявку с уникальными `id` и `number`, сохраняет её со статусом `New` и отображает заявку в списке.

**Результат:** Да / Нет.

---

## AC-02. Назначение исполнителя

**Дано:** существует созданная заявка со статусом `New`.

**Когда:** диспетчер отдельно назначает исполнителя.

**Тогда:** система сохраняет назначенного исполнителя, при этом статус заявки остаётся `New`.

**Результат:** Да / Нет.

---

## AC-03. Перевод заявки в работу

**Дано:** исполнитель вошёл в систему и ему назначена заявка со статусом `New`.

**Когда:** исполнитель переводит свою заявку в статус `InProgress`.

**Тогда:** система изменяет статус заявки на `InProgress`. Другой исполнитель не может изменить статус этой заявки.

**Результат:** Да / Нет.

- автоматические уведомления о нарушении сроков;
- интеграция с внешними информационными системами;
- интеграция с BIM-системами;
- интеграция с ГИС;
- мобильный сбор информации непосредственно на объекте.
